# Show-time retrain of the release (SM92) integration — 2026-11-04

The show-time retrain of the release (SM92) replaces the small model, leak-free, cool-down from epoch 25 (SM72, [integration report](rwkv-sm72e25-2026-10-30.MD)) as the default small model. To keep the two apart, the new weights have the profile key `sm92` and the folder `qt/aqt/rwkv_inference/sm92/`; `sm72e25` (with its own answer-time head), `sm72e20` and `sm72` stay bundled. Deck Options → RWKV → Advanced → **Use Smaller Model** selects `sm92` when on and the Legacy big model when off. New profiles and profiles without a supported saved choice default to `sm92`. Existing explicit selections continue to load; a successful ordinary Deck Options save upgrades SM40, SM36, SM55, SM56, `sm72`, `sm72e20` or `sm72e25` to `sm92`. Discard, a failed save and parameter-only optimization preserve the saved selection. Reopen the profile to apply a saved change. Storage precision and f32 computation are unchanged.

A new key (instead of replacing the weights under `sm72e25`) is deliberate: cached RWKV state is tied to the model identity, so a profile that was saved with the earlier weights must not silently reuse state computed with different ones.

## What changed and why

The review log records, for each review, the time from the card's previous answer to this answer. That interval includes the time spent answering the card, which Anki cannot know when it shows the card. SM72 learned every prediction from these answer-to-answer intervals. Anki, however, asks the model for its Instant prediction (and for the Curve at the current time) when the card is shown: the interval it gives is the time from the previous answer to the moment of showing. SM72 was therefore queried with intervals that are systematically a little shorter than the ones it learned from. Upstream measured the cost: scored on show-time inputs, SM72 loses 0.128 points on Curve and 0.428 points on Instant against its own answer-to-answer score.

SM92 is SM72 trained further on the inputs Anki gives. It starts from SM72's epoch-25 weights, adds one constant-LR epoch and then SM72's exact one-epoch 32k Muon cool-down (same 8,000 users, order, seeds and distillation targets from the big model (1 leak-free epoch)), both with the training option `show_time_intervals`:

| Row | Interval used (seconds) | Cumulative interval |
| --- | --- | --- |
| Query of review j (Instant head, and the Curve query time for review j) | `floor(max(elapsed_seconds_j − duration_j / 1000, 0))`: previous answer to the moment review j is shown | the card's committed answer-to-answer intervals + that interval |
| Committed answer of review j | `elapsed_seconds_j`: previous answer to answer j | the card's answer-to-answer intervals up to and including j |

The sin/cos encodings use the same seconds; the day-based `elapsed_days` inputs are unchanged.

## The fork already builds these inputs

No feature-builder change is needed. In the live paths a query's interval is the current time minus the card's last answer time (`card.last_review_time`, or the creation time for a first review where configured), a committed answer's interval is its answer time minus the previous answer's (`_rwkv_answer_elapsed`, history replay in `rslib/src/scheduler/rwkv.rs`), and `FeatureState::features_for` adds the row's interval to the card's running sum of committed intervals, which only `store_review` advances. That is exactly the training rule above, for query and commit rows alike. The new test `rwkv_sm92_feature_builder_matches_show_time_intervals` feeds each published row its own interval and checks the native feature builder's interval inputs (features 0–7) against the trainer's: on the full release vectors, all 6,543 queries and 7,860 committed answers match within 7.5e−7.

## Answer-time head

The answer-time head on richer frozen features (SM82c) reads the small model's internal states, so SM72's head is not valid for SM92's weights. It was retrained with the exact SM82c recipe on the frozen SM92 model (same 1,991 training users, first 400,000 reviews each, one pass, AdamW, head only; every SM92 weight bit for bit unchanged) and ships as `qt/aqt/rwkv_inference/sm92/time_head.f32.bin` (format version 1, 69,056 parameters). Gate fixed before training: time LogLoss on the same evaluation within +1% of SM82c's 1.9568.

From the decision of the answer-time head on the frozen SM92 model, anki-rwkv branch `sm92` (`artifacts/small-model/sm92/head/sm92-head-decision.md`, commit `0ecbace51`). Training: one pass over 80,988,171 labelled reviews of 1,991 users, 9,887 AdamW steps, head only. Evaluation: the same 722 users of the 732-user set and the same 21,585,938 later-day test reviews with a recorded time as the answer-time head on richer frozen features (SM82c), on the same inputs (the review log's answer-to-answer intervals). ## Verification

The RWKV module tests were compiled and run on Windows x86-64 (CPU only, GNU toolchain) in the standalone Cargo harness of the earlier integrations (a copy of `rslib/src/rwkv/` and `rslib/io/` with stand-ins for the generated protobuf and crate items it imports, SQLite linked dynamically); the full desktop build (protoc, ninja, a C compiler) was not available on that machine.

- Default features (small primary engine): 253 tests, 219 passed, 30 ignored, 4 failed. Without default features (Legacy primary engine): 252 tests, 219 passed, 29 ignored, 4 failed. The four failures are the bit-exactness checks of the experimental fused packed INT4 kernels (`fused_packed::tests`, in both engines), the same four that failed before this change; they are test-only benchmark code.
- New tests: `rwkv_sm92_matches_published_vectors`, `rwkv_sm92_ignores_missing_id_flags_in_every_inference_path`, `rwkv_sm92_feature_builder_matches_show_time_intervals`, `rwkv_sm92_answer_time_history_matches_published_features` and `rwkv_sm92_answer_time_head_matches_published_vectors`, run on the bundled fixtures and, through the environment variables, on the full package vectors. The runtime, restore and architecture tests include the new model.
- Desktop and browser tests were updated in the existing style (model defaults, save migration from `sm72e25` too, bundled file paths, embedded backend configuration) but could not be run on this machine (no pytest, PyQt or Node there); the remote CI runs them. The model-key module `aqt.rwkv_model` was loaded directly: the default and unsupported values resolve to `sm92`, and the bundled file of every key exists.
- `rustfmt --edition 2021 --check` reports no changes for the edited Rust sources.

## Not done

- No matched backup or own-collection comparison for these weights.
- INT4 card state was not scored upstream for these weights; the desktop's default mixed INT4-card/INT8-note storage is covered by the native restore test but not by accuracy vectors.
- The answer-time head was trained, as SM82c, on the review log's answer-to-answer query intervals, and is queried with show-time intervals like SM72's head; its show-time accuracy was not scored separately.
- The desktop feature builder's entity codes and calendar phases differ from the training scorer's; the effect on accuracy was not measured upstream.
